# 演出道具交接核验 Web 应用

用 **Node.js（Express）+ 原生 HTML/CSS/JavaScript** 实现的演出道具交接核验工具。
录入道具与「按分钟标记」的交接记录（道具、交出者、接收者），应用按时间重放记录、
连成每件道具唯一的交接链，自动定位冲突并提示演出结束仍未归仓的道具；
支持**批量交接预演**——按行填写整批交接，先合并重放、逐件给出提交后的持有人或冲突，
全部通过后一次写入；并支持演出中途的**现场盘点**——选定分钟、逐行填报实物持有人，
即时给出该时刻的账实差异。

## 一条命令启动（Docker Compose）

```bash
docker compose up -d --build
```

启动后访问：

- **应用地址：** <http://localhost:3000>
- 核验结果接口（JSON）：<http://localhost:3000/api/verify>
- 批量交接预演接口（POST JSON）：`http://localhost:3000/api/records/batch/preview`，页面入口为右上角「🧪 批量交接预演」
- 现场盘点接口（POST JSON）：`http://localhost:3000/api/inventory/check`，页面入口为右上角「🔍 现场盘点」

停止：

```bash
docker compose down
```

> 首次启动时会自动安装依赖；数据文件不存在时会自动初始化一份演示数据（4 件道具，
> 分别覆盖「正常归仓 / 多条可接续冲突 / 断链冲突 / 结束未归仓」四种情形），
> 便于直接看到核验效果。删除 `data/store.json` 后重启可恢复初始演示数据。

## 必要配置

配置通过环境变量 / Compose 完成，均有默认值，通常无需修改：

| 配置项 | 默认值 | 说明 |
| --- | --- | --- |
| `HOST_PORT`（compose） | `3000` | 宿主机映射端口。换端口：`HOST_PORT=8080 docker compose up -d --build` |
| `PORT`（容器内） | `3000` | 服务监听端口，修改时需同步修改 `docker-compose.yml` 的端口映射右侧与 healthcheck |
| `DATA_FILE`（容器内） | `/app/data/store.json` | 本地 JSON 数据文件路径 |
| 数据持久化卷 | `./data:/app/data` | 数据保存在宿主机 `./data/store.json`，重建容器不丢数据 |

非 Docker 本地运行（需要 Node.js ≥ 18）：

```bash
npm install
npm start          # 默认 http://localhost:3000
PORT=8080 DATA_FILE=./data/store.json npm start
```

## 使用说明

### 数据录入

- **录入道具**：名称（必填，不可重名）+ 备注。每件道具初始持有人恒为「仓库」。
- **录入交接记录**：选择道具、填写分钟（非负整数）、交出者、接收者（二者不可相同）、备注。
- 道具与记录均可随时**修改、删除**；删除道具会级联删除其名下全部记录。
- 每次增删改后自动重新核验，也可点击右上角「↻ 重新核验」手动重放。

### 核验规则

1. 每件道具初始归「仓库」。
2. 取该道具的全部记录按**分钟升序**逐分钟重放。
3. 在同一分钟内，把记录视为有向边，从当前持有人出发寻找交出者匹配的记录：
   - **恰好 1 条可接续** → 执行交接，持有人变为接收者，并可继续匹配本分钟剩余记录
     （因此同一分钟内 `A→B、B→C` 的链式交接，无论以什么顺序录入都能识别）；
   - **存在 ≥ 2 条可接续记录**（当前持有人同时要交给多个人）→ 判定为
     **「多条可接续记录」冲突，交接链不唯一**，定位这些记录并说明原因；
   - **该分钟有记录但没有一条能从当前持有人交出** → 判定为
     **「剩余记录无法接续（断链）」冲突**，定位当前持有人与冲突分钟的记录。
4. 记录全部重放完毕后，持有人仍不是「仓库」→ 提示**演出结束未归仓**。
5. 引用了已删除道具的记录会被标记为「孤儿记录」，不参与任何道具的核验。

### 批量交接预演（整批录入）

点击右上角「**🧪 批量交接预演**」（应用地址 <http://localhost:3000>）：按行填写
**道具、分钟、交出者、接收者**（校验规则与单条记录完全一致），点击「开始预演」后逐件查看结果，全部通过才能「确认提交」。

预演与提交规则：

1. **预演不落盘**：服务端把整批记录与当前数据合并，沿用同分钟唯一链规则整体重放，
   只返回即时结果，不改写任何交接记录。
2. **逐件结论**：每件受影响道具给出「提交后的持有人」（已归仓 / 演出结束未归仓，未归仓不阻止提交）
   或冲突说明，并**定位涉及的批次行号**（点击行号可滚动高亮对应批次行，冲突行整行标红；
   冲突命中的既有记录编号一并给出）。
3. **禁止提交**：受影响道具**原本已冲突**（即使本批次恰好能接续）或**合并后冲突**时，
   标明原因并禁止提交，需先处理冲突再重新预演。
4. **提交需重新核对**：提交时服务端核对预演所用的**数据版本**与**整批内容指纹**，
   预演后数据被修改（版本过期）或批次内容有任何改动，都会返回 `409` 要求重新预演。
5. **一次写入**：核对通过后单次落盘写入全部记录（临时文件 + 原子重命名），不会留下部分记录；
   写入后页面自动刷新记录列表与核验结果。

### 现场盘点（演出中途）

点击右上角「**🔍 现场盘点**」：选择盘点时刻（非负整数分钟），逐行填写
**道具名称 + 该时刻实物持有人**（可点「按已登记道具补齐」快速生成待填行），提交后页面展示账实差异表。

盘点规则：

1. 服务端**只重放盘点分钟及以前**的交接，沿用上面的同分钟唯一链规则，
   并在**该分钟所有交接完成后**取账面持有人；晚于盘点时刻的记录与冲突不影响本次盘点。
2. 盘点行逐行定性：
   - **一致**：名称已登记、链可重放，实物持有人与账面持有人相同；
   - **持有人不符**：名称已登记、链可重放，但实物持有人与账面持有人不同（同时给出账面持有人）；
   - **账外**：名称未在道具清单登记；
   - **重复录入**：同一名称在盘点行出现多次——每行**单列**、不以后项覆盖前项，且不参与账实比对；
   - **无法判定**：名称已登记，但其交接链在盘点分钟及以前已冲突（账面持有人不可知）；
   - **未盘**：已登记道具在盘点单中完全没有出现（系统补列一行，持有人留空）；未盘道具若此前已冲突，同样标为「无法判定」。
3. 结果顶部按类别汇总并给出「账实差异」行数（除「一致」「重复录入」外均计为差异）。
4. 盘点**只生成即时结果，不改写任何交接记录**；切换页面数据后旧结果可直接关闭。

### 界面展示

- 顶部汇总：道具总数、已归仓、冲突数、未归仓数、无记录数、演出末分钟。
- 每件道具一张核验卡片：
  - 状态徽章：✓ 已归仓 / ⚠ 演出结束未归仓 / ✕ 交接链冲突 / — 无交接记录；
  - 冲突说明：冲突类型、发生分钟、当前持有人、**定位到的冲突记录编号**（点击可滚动到右下表中对应行并红色高亮）；
  - **持有时间轴**：按分钟时长比例绘制的彩色分段（灰=仓库、蓝=人员、黄斜纹=结束未归仓、红斜纹=冲突点），悬停查看每段的持有人与起止分钟；
  - 交接链：`仓库 → 张三 [第0分] → 李四 [第3分] → …`。
- 右下记录表中，所有被定位为冲突 / 孤儿的记录整行标红。

## 数据存储

数据保存在本地单个 JSON 文件（默认 `data/store.json`）：

```json
{
  "version": 1,
  "rev": 7,
  "props":   [{ "id": "p_xxx", "name": "青龙剑", "note": "...", "createdAt": 1700000000000 }],
  "records": [{ "id": "r_xxx", "propId": "p_xxx", "minute": 3, "from": "张三", "to": "李四", "note": "...", "createdAt": 1700000000000 }]
}
```

其中 `rev` 为数据版本号，每次落盘自增，批量交接预演以此核对预演后数据是否被修改。

写入采用临时文件 + 原子重命名；可直接备份 / 编辑该文件，重启后生效（结构损坏时会自动备份并重置为初始数据）。

## HTTP API

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/state` | 全部数据（含数据版本号 `rev`）+ 核验结果 |
| GET | `/api/verify` | 仅核验结果 |
| POST | `/api/records/batch/preview` | 批量交接预演：提交 `{ rows: [{propId, minute, from, to, note?}] }`，合并当前数据重放，逐件返回提交后的持有人或冲突（含涉及的批次行号）与 `previewId`；只读不落盘 |
| POST | `/api/records/batch/commit` | 批量提交：提交 `{ previewId, rows }`，核对预演数据版本与整批内容指纹，不一致返回 `409` 要求重新预演；通过后一次写入全部记录 |
| POST | `/api/inventory/check` | 现场盘点：提交 `{ minute, rows: [{name, holder}] }`，返回该分钟账实差异（只读，不写数据） |
| GET/POST | `/api/props` | 道具列表 / 新增道具 |
| PUT/DELETE | `/api/props/:id` | 修改 / 删除道具（删除级联清理记录） |
| GET/POST | `/api/records` | 记录列表 / 新增记录 |
| PUT/DELETE | `/api/records/:id` | 修改 / 删除记录（修改保留原录入时间） |

## 项目结构

```
.
├── Dockerfile               # Node 20 Alpine 镜像，构建期 + 启动时安装依赖
├── docker-entrypoint.sh     # 容器启动入口：安装依赖 -> 启动（首次初始化数据）
├── docker-compose.yml       # 单服务编排：端口、数据卷、健康检查
├── server.js                # Express 服务：静态页 + JSON API
├── src/
│   ├── store.js             # 本地 JSON 存储（首次启动写入初始演示数据；rev 数据版本号）
│   ├── verify.js            # 交接核验引擎（按分钟重放 / 冲突定位 / 时间轴 / 盘点时刻账面持有人）
│   ├── inventory.js         # 现场盘点分类引擎（一致 / 不符 / 账外 / 重复 / 无法判定 / 未盘）
│   └── batch.js             # 批量交接预演引擎（合并重放 / 逐件结论 / 批次行号定位 / 内容指纹）
├── public/                  # 原生前端（无构建步骤）
│   ├── index.html
│   ├── styles.css
│   └── app.js
└── test/
    ├── verify.test.js       # 核验引擎单元测试（node test）
    ├── inventory.test.js    # 现场盘点引擎单元测试
    ├── batch.test.js        # 批量预演引擎单元测试
    └── batch-api.test.js    # 批量预演 / 提交接口集成测试（真实 HTTP 全流程）
```
